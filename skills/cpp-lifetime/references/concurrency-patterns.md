# 并发模式

设计线程池、任务队列、关闭流程、原子操作或无锁结构时阅读。优先沿用项目已验证的同步组件和执行器。

## 线程池与任务队列

- 队列有容量上限；满时的策略（阻塞提交者、拒绝并返回错误、丢弃最旧任务）写进接口合同。
- 任务持有执行所需资源的所有权，或持有能证明资源存活的句柄；提交时的借用在执行时可能已经失效。
- 提交失败（队列满、正在关闭）时，提交者负责回滚已申请的额度和资源。
- 任务中的异常或错误要被记录或返回给等待方，不能静默丢失；不能让一个任务的失败终止工作线程。
- 不在持锁时执行任务或调用外部回调。

## 关闭顺序

1. 停止接受新任务（设置关闭标志或关闭入口），之后的提交返回明确错误。
2. 取消或排空在途任务，等待它们确认结束。
3. 通知并 `join` 工作线程（`std::jthread` 会在析构时请求停止并 join）。
4. 释放任务可能访问的资源。

析构函数中执行上述流程时，确认不会在持有其他对象的锁时阻塞，也不会在工作线程自身中被调用（自我 join 会死锁）。

## 锁的选择

- 默认用 `std::mutex`；读远多于写且临界区较长时才考虑 `std::shared_mutex`，它的开销比普通互斥锁大。
- 锁的粒度按不变量划分：需要共同成立的字段由同一把锁保护。热点数据可以按 key 分片加锁。
- 多把锁用 `std::scoped_lock` 一次获取，或定义全局一致的加锁顺序并在注释中写明。

## 原子操作与内存序

- 只保护单个独立值（计数器、标志、指针替换）时才用原子变量；多个字段之间有约束时用锁。
- 默认使用 `seq_cst`。使用更弱的内存序时写明配对关系：
  - `release` 写与 `acquire` 读配对，保证写入方在 `release` 之前的写入对读取方可见；
  - `relaxed` 只适合不用来发布其他数据的计数器和统计量；
  - 引用计数递减通常需要 `acq_rel`（或 `release` 递减加 `acquire` 栅栏），才能安全地析构对象。
- `compare_exchange_weak` 可能虚假失败，放在循环中使用；单次尝试用 `compare_exchange_strong`。
- C++20 的 `std::atomic::wait`/`notify_one` 可以替代自旋等待加条件变量的组合。

## 无锁结构与内存回收

- 只有在锁已被测量为瓶颈时才引入无锁结构，并优先使用成熟实现（Folly、oneTBB、moodycamel::ConcurrentQueue）。
- 无锁结构的难点在于回收：一个线程摘下节点后，其他线程可能仍在读它。需要明确的回收机制：
  - hazard pointer：读者发布正在访问的指针，回收者跳过被发布的节点（Folly `hazptr`；C++26 加入了 `std::hazard_pointer`）；
  - 基于 epoch 的回收：所有读者离开旧 epoch 后统一释放；
  - RCU：读端几乎没有开销，写者在宽限期结束后释放（liburcu；C++26 加入了 `std::rcu`）。
- 使用 CAS 的结构要处理 ABA：同一地址被释放后重新分配，比较仍然成功。用 tagged pointer、版本号或上述回收机制避免。

## 伪共享与线程局部状态

- 不同线程频繁写入的变量放在不同缓存行（`alignas(64)` 或 `std::hardware_destructive_interference_size`，见 `cpp-core` 技能的内存参考）。按线程或按核心分片计数，读取时汇总。
- `thread_local` 对象在线程退出时析构，析构顺序与其他线程无关；线程池中的 `thread_local` 会跨任务保留状态，不要用它传递任务上下文。

## 测试

- 用 `std::latch`/`std::barrier` 或手动驱动的执行器构造确定的交错，测试关闭时仍有任务在提交、任务执行中被取消、队列满等情况。
- TSan 单独构建运行；它发现数据竞争，但不证明协议正确或没有死锁。
- 压力测试作为补充：固定随机种子、记录失败时的种子，便于复现。
