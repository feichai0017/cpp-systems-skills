# C++ 分支评审

评审的默认产物是发现与验证结论。用户要求修复时才修改代码；遵循用户指定的评审格式及项目约定。

## 确认评审对象

1. 记录仓库、HEAD、目标分支/base、提交范围与是否包含本地改动。优先使用用户给定范围和 PR/MR 元数据；不要猜 `main`，不要把下层 MR 当作本层改动。
2. 区分 `merge-base(base, head)..head` 的已提交改动、HEAD→index、index→working tree 与 untracked 文件。每层单独读取；同一文件可能在多层变化或互相抵消。
3. 比较指定的两个快照时使用明确的两端 diff；PR 分支评审通常用 merge-base。合并提交、重定基线和浅克隆需要说明实际语义。
4. 基线不可解析或多个 merge-base 时先取得正确提交/确认范围，禁止悄悄回退到另一个分支。获取远端数据需服从当前环境权限。

可用内附只读脚本生成范围清单。脚本路径相对本技能目录，`--repo` 指向被评审项目：

```sh
python3 scripts/review_scope.py --repo /path/to/project --scope all --base origin/stack-parent
python3 scripts/review_scope.py --repo /path/to/project --scope branch --base origin/stack-parent --head feature
python3 scripts/review_scope.py --repo /path/to/project --scope worktree
```

输出包含固定 commit ID、各层文件与读取补丁的命令。它不抓取远端、不选 base、不修改 index，也不读取 untracked 的内容。按需查看这些文件；不要自动打开凭据、二进制或体积很大的产物。检查 `.gitmodules` 与 submodule gitlink 改动时要单独说明其内容是否已取得。

清单不是原子快照。本地有并发编辑时，记录状态变化并在结论前重新确认相关范围；不要声称清单覆盖了之后才出现的改动。

## 从外部可观察行为开始

- 读接口、调用方与相邻测试，确认变化会在哪个真实场景触发。
- 检查长度/形状/顺序/单位、错误与部分结果的合同；拒绝用截短、吞错、扩大容差掩盖不一致。
- 追踪资源 owner、借用、异步完成和释放；检查变化是否破坏现有 retry、ACK、quota、generation、read guard 或 shutdown 保护。
- 检查锁序、同步关系、复合状态与取消竞争；区分智能指针寿命保证和对象线程安全。
- 评估 API/ABI、布局、序列化和编译条件是否受影响；基于项目承诺判断，不假定所有内部接口都需要长期兼容。
- 对新增抽象问清职责；删除检查要有上游保证与有效范围。性能担忧需要明确成本路径，不能仅凭代码形状宣称回退。
- 对新增通用组件搜索仓库和已引入库的同类实现，检查是否重复建设。引用开源设计时核对实际版本、机制与本地前提差异，不因参考项目成熟就默认实现正确。
- 检查语义命名：动作与查询、单位、容量与大小、发起与完成是否区分。工具检查通过不证明名称与行为一致。

## 验证与发现

能低成本复现时运行相关构建/测试。重要问题应有精确的触发条件、调用/数据路径和具体影响；没有复现时明确依据及置信限制。

每个问题包含：优先级、紧凑的文件/行定位、触发场景、错误行为、最小修正方向。区分本次引入的问题、已有问题和可选风格建议，不让偏好淹没缺陷。

最后说明实际评审范围、已执行验证及剩余风险。没有可操作问题就明确写出，并保留验证边界；不要凑数。
