# C++ 性能分析

先说明业务场景、指标与正确性合同，再选择测量或优化。使用项目现有 benchmark/profiler；没有数据时给出待验证假设，不编造收益。

## 明确问题

- 请求模式、输入形状、batch、并发、冷热状态、数据大小、设备/NUMA 布局和服务目标是什么？
- 用户关心端到端延迟、尾延迟、吞吐、CPU 占用、内存峰值，还是某个 kernel？不要拿另一个指标替代验收。
- 哪些硬件与生产路径可用，哪些只是模拟？先确认可测范围，再安排实验。

## 追踪实际成本

沿真实调用链写出字节路径：

`源数据/owner → 读取 → 分配/转换/打包 → staging → 传输/拷贝 → 目标写入 → 消费 → 回收`

标明每段所在进程、线程、内存介质/设备，以及同步或异步完成点。按问题检查：分配与引用计数、缓存局部性、NUMA 远端访问、锁竞争、调度、序列化、系统调用、设备与网络等待。

区分“代码存在某路径”“计数器确认实际走过”“profiler 显示消耗”“对照实验确认收益”。少一次调用或少一层包装不等于已经证明更快。

## 建立可比较实验

- 记录基线与候选 commit、编译器与 flags、依赖、硬件、线程/亲和性、输入、缓存状态和运行命令。
- 基线与候选保持同等工作量和语义；先验证长度、内容、顺序和精度等必要合同。不能用少读数据、减少计算或放宽容差换速度。
- 根据指标设置 warm-up、重复次数和采样窗口，保留原始样本与波动。交替/交错运行可减轻机器状态漂移；不要只挑最快一次。
- 热缓存与冷启动分别测；microbenchmark 与端到端分别报告。测异步操作时明确计时覆盖提交还是实际完成，不能只计 enqueue。
- 把工具开销、并发背景负载、热节流、频率和缓存污染列入解释范围，只记录与当前问题相关的项。

需要整理实验结果时使用 [证据记录模板](references/evidence.md)，按实际项目裁剪。

## 改动与结论

优先处理证据支持的主导成本。保留 ownership、校验边界、retry、ACK、quota、completion 和 read-lifetime 保证；移除等待要证明替代依赖保持正确顺序。

不预设 SIMD、lock-free、巨页、特定 allocator 或额外缓存一定更优。引入时说明成本模型、适用负载及实测结果。

收益写清基线、候选、单位、样本与范围。延迟下降 `(baseline-candidate)/baseline`，吞吐提升 `(candidate-baseline)/baseline`，speedup 为相应可比较时间比；分母为零或样本不可比时不报比例。

最终区分已确认事实、证据支持的推断、待验证假设和环境限制。实验未显示收益时如实报告；不继续堆优化来掩盖结果。
