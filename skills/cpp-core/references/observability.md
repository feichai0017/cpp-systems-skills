# 可观测性：日志、指标、追踪与崩溃诊断

添加日志、指标、追踪、断言或崩溃处理时阅读。沿用项目已有的日志库、指标体系和命名约定。

## 日志

| 级别 | 用途 |
| --- | --- |
| ERROR | 需要人处理的失败：请求失败且无法自动恢复、数据损坏 |
| WARNING | 已自动处理但值得关注：重试成功、降级、配置使用了默认值 |
| INFO | 生命周期事件：启动、配置摘要、连接建立与关闭、关闭完成 |
| DEBUG / VLOG | 排查问题时临时开启的细节，默认关闭 |

- 每个错误只在被处理（恢复、转换成对外错误或终止）的地方记录一次；中间层只传递并补充上下文。
- 日志带上定位所需的标识：请求 id、连接、文件、offset、generation。优先结构化的键值，而不是只能人读的句子。
- 热路径上的日志按频率限制或采样（例如每 N 次或每秒一次），避免日志本身成为瓶颈。
- 不记录密钥、令牌、用户数据内容；必要时记录长度或哈希。
- 信号处理函数中不能写日志（见 OS 接口参考）。
- 异步日志的队列满时的策略（阻塞、丢弃、计数）要明确；进程正常退出和崩溃前都要尽量刷出缓冲。

## 指标

| 类型 | 用途 | 示例 |
| --- | --- | --- |
| 计数器 | 只增不减的累计值 | `requests_total`、`bytes_read_total` |
| 仪表 | 可升可降的当前值 | `queue_depth`、`open_connections` |
| 直方图 | 分布与分位数 | `request_latency_seconds`、`batch_size` |

- 名称带单位后缀（`_bytes`、`_seconds`、`_total`），与项目约定一致。
- 标签的取值必须有限：不要把请求 id、用户 id、文件路径作为标签，否则序列数会无限增长。
- 热路径上更新指标使用无锁计数或按线程分片后汇总，不要每次更新都加全局锁。
- 记录拒绝、重试、超时和降级的次数，它们是背压和故障的早期信号。

## 追踪

- 一个请求的生命周期用 span 表示，跨线程、跨进程传递追踪上下文（OpenTelemetry 或项目已有方案）。
- span 覆盖实际完成点：异步操作在完成回调中结束 span，而不是在提交时结束。
- 帧级或微秒级的性能分析用 Tracy、Perfetto 一类工具，与面向服务的分布式追踪分开。

## 断言与终止

- 不变量被破坏时立即终止并输出上下文（相关变量的值、对象状态），不要继续运行在损坏的状态上。
- 始终启用的 `CHECK` 用于即使在 Release 中也必须成立的条件；`DCHECK`/`assert` 只用于调试构建。
- 终止前尽量刷出日志缓冲；崩溃处理代码本身要尽可能简单。

## 崩溃诊断

- 生产环境开启 core dump（`ulimit -c`、`systemd-coredump`），并保留带调试信息的二进制或独立的符号文件，用于事后分析。
- 致命信号时打印符号化的调用栈：项目已有方案、`absl::FailureSignalHandler`，或 C++23 的 `std::stacktrace`（标准库支持有限，GCC 需要额外链接）。信号处理中的栈打印必须使用异步信号安全的实现。
- sanitizer 构建的报告（ASan、TSan、UBSan）包含精确的位置和调用栈，测试环境中优先使用。

## 健康检查与调试接口

- 区分存活（进程还在运行）与就绪（可以接收流量）：依赖未就绪、正在关闭或积压过多时报告未就绪。
- 调试接口（状态转储、配置查看、动态调整日志级别）只在受信网络或经过认证后可访问。
