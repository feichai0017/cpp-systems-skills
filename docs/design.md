# 设计取舍

## 工作场景

面向已有 C++ 系统：需求实现、代码精简、分支评审、异步资源生命周期、构建验证以及性能分析。常见风险是把所有权与并发合同藏在包装层后面，或在“精简”过程中移除实际保护；另一个风险是将源码推断、单元测试和端到端性能混成一个结论。

这里所说的借鉴 Rust，是明确 owner/borrow、让类型表达不变量、显式错误和受约束的状态迁移，不是在 C++ 上复制 Rust 语法或声称具有借用检查器保证。

## 三种组织方式

| 方案 | 收益 | 代价 |
| --- | --- | --- |
| 一个大 skill | 入口单一 | 小修改也容易加载并发、设备和性能细节 |
| 底座 + 五个场景技能（采用） | 按任务选择，独立安装，边界清楚 | 少量项目优先原则需要在独立入口重复 |
| 每个工具/语言特性一个 skill | 技术主题细 | 触发重叠、维护与组合成本高，容易从业务目标偏到工具 |

## 职责划分

`cpp-core` 将简化实现、代码规范和语义命名前置为日常默认要求，写码和交付前均检查；所有权、错误与并发保护约束简化的适用范围。`cpp-lifetime` 针对资源从创建到实际完成/回收的完整链路；`cpp-simplify` 用于专门的精简任务，对删除与合并提出证据要求；`cpp-review` 负责范围正确和发现质量；`cpp-validation` 负责执行与证据；`cpp-performance` 负责成本路径与实验可比性。

不引入总调度 skill。各技能显式允许隐式调用，描述将场景词放在开头，避免初始目录描述被缩短后丢失主要触发信息。个人或项目 `AGENTS.md` 中的简短选择规则负责“写 C++ 默认使用 cpp-core”，其他任务按需补充专项。它是默认行为指令，不是客户端提供的确定性路由器；不能凭配置通过就声称每个任务都已正确选中技能。

各技能保持独立可用。正常实现不自动加载全部技能，不擅自创建任务或调用子代理；全局默认示例和项目示例均保留用户指令与项目约定的优先级。

## 适配项目而不覆盖项目

- 已有 C++ 标准、Status/Result、命名、文件后缀与工具配置优先。
- 不强制异常、concepts、CMake、第三方错误库、全量 clang-tidy 或全局 warning 策略。
- 复用现有所有权与同步协议；删除校验需要证明保证在本次使用前一直有效。
- 新增组件前搜索仓库和实际依赖版本；外部源码研究只在现有能力不足或设计复杂时触发。直接调用、引入依赖和参考适配分别判断成本。
- 命名形式交给项目工具，语义命名仍检查动作/查询、单位和实际完成点。
- DuckDB 作为主要外部 C++ 工程参考，固定相关源码版本并区分观察与迁移判断；将断言边界、安全包装、pin 与表示转换落实到相关技能，保留现有错误框架和基础类型。
- 项目参考与依赖选型分开维护：LLVM 补充工程规范，LevelDB/RocksDB、Arrow、Seastar 按机制读取；基础库按地址稳定性、ABI、执行器和回收合同选择。两个索引均留在 `cpp-core` 包内，不要求普通任务加载全表。
- 共享内存与状态服务另按实际场景索引固定源码版本。Vineyard、Plasma、LMDB 和 iceoryx 只提供匹配的局部机制，不成为默认依赖或本地类层次模板。
- 只复用相同职责。冷热路径可以共享纯计算，但路径各自的 owner、验证和 completion 不因代码相似而合并。
- 涉及内容/长度/精度的合同用严格对照验证；性能优化不能通过减少实际工作量获得表面收益。
- 不要求每个修改写长计划、增加测试或走新审批。当前用户要求、授权与环境限制仍然有效。

## 包装与工具

每个目录提供标准 YAML frontmatter、简短 `SKILL.md` 和 Codex UI 元数据。条件参考包括复用与源码研究、跨边界合同、工具配置、性能证据模板。每个入口限制在 200 行内，这是本仓库的上下文预算，不是通用标准。

参考文件留在所属技能中；不能用相对链接依赖兄弟技能或仓库 docs。校验器检查包内边界，测试再逐个独立安装并检查引用。独立入口只重复必要规则，不要求安装其他技能。

`review_scope.py` 只读 Git 元数据，保留 committed/staged/unstaged/untracked 四层，并输出读取补丁的命令。它拒绝猜 base 和混用非当前 head 的工作区，避免堆叠分支漏审与误审。

`install.py` 复制自包含目录；目的位置由调用者指定，冲突前置检查，不自动覆盖和更新。脚本运行仅需 Python 标准库；维护检查另外使用 PyYAML。

## 验收边界

交付需要：六个有效技能目录、可读的触发描述、可解析的 UI 元数据、独立安装后可达的内部引用、可运行的辅助脚本、具有行为意义的工具测试、安装说明和公开仓库。

结构校验和脚本测试不能证明指令质量。行为案例分别覆盖错误策略、单次 RAII、可变状态检查、MR 栈、短读、异步完成计时等误用；试用时记录实际模型输出，再据此收敛规则。工具检查、模型完成案例与技能带来的效果提升分别判断。

仓库维护评测输入、判据和工具，不维护单次实验结果。模型输出、补丁、日志、输入快照或摘要、成绩与运行报告保存在仓库外；不把案例存在或结构校验通过表述成模型评测已完成。
