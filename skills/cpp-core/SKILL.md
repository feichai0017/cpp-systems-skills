# C++ 日常编码

日常编码默认以现代写法、简化实现、代码规范和语义命名为重点，在保持业务行为、所有权和错误/并发合同的前提下完成最小必要实现。这些要求都适用于普通写码，无需用户额外提出。

日常写 C++ 时默认使用本技能，无需用户点名。已安装专项技能时，仅在任务确实涉及其职责时补充；不因日常简化要求就自动加载完整 `cpp-simplify` 流程。本技能单独安装也可完成日常编码；不为小修改制造设计文档、审批或全套审计。

## 先确定项目事实

- 读取适用的 `AGENTS.md`、相关接口与调用方、构建入口和最近邻测试。当前用户要求及项目约定优先于本技能的默认建议。
- 确认实际 C++ 标准、编译器、构建系统（CMake、Blade 或其他）、异常/RTTI 策略、错误类型、命名、文件后缀和格式化配置。标准从构建文件或实际编译命令读取，不猜测、不擅自升级。
- 确认可用的库范围与移植约束：README、构建选项和配置宏可能要求关闭 STL、同一源文件也按 C 编译、不依赖异常/RTTI 或停留在 C++98/03。这些约束优先于下文的现代写法默认值；在其范围内使用项目自己的容器、字符串和 owner，不引入被排除的头文件与特性。
- 用一句话说明要改变的行为及验收条件。缺失信息会改变兼容性、所有权或外部行为时再澄清；其他情况按已有约定推进。

## 现代 C++ 写法

在项目已确定的标准和库范围内用足它允许的设施：不升级标准，也不写低于该标准的旧式代码。项目已有等价类型（`Status`、`Result`、span、日志与断言宏）时用项目类型。新项目没有约束时以 C++20 为基线。具体写法、按标准的设施表和对照示例见 [现代 C++ 写法](references/modern-idioms.md)。

下列默认值以 C++11 及以上且可用标准库为前提。C++98/03、关闭 STL、与 C 共用源文件或无异常的代码，按 [现代 C++ 写法](references/modern-idioms.md) 中“旧标准与受限库范围”一节处理。

- **所有权**：不写裸 `new`/`delete`/`malloc`。独占用 `std::make_unique`，确需共享寿命才用 `std::make_shared`。包装 C 句柄用 `std::unique_ptr` 加删除器 struct，不用函数指针删除器（它让 `unique_ptr` 变大一倍并多一次间接调用）。
- **特殊成员**：优先 Rule of Zero；自定义 owner 时同时决定复制、移动与析构，删除不该有的复制，移动操作 `noexcept`。单参数构造函数 `explicit`；覆盖虚函数写 `override`/`final`。
- **参数与返回**：只读字符串用 `std::string_view`，只读连续序列用 `std::span`（C++20）或项目的等价类型；要保存的参数按值接收再 `std::move`；结果通过返回值传递，不用输出参数。返回 `Status`/`Result` 的函数标 `[[nodiscard]]`。
- **错误**：可失败操作返回项目的 `Status`/`Result`，C++23 可用 `std::expected`；`std::optional` 只表示合法缺席。文本转数字用 `std::from_chars`，不用 `atoi`/`stoi`。
- **类型**：`enum class`、`using` 别名、`nullptr`、`constexpr` 常量；类型转换用 `static_cast`/`std::bit_cast`，不用 C 风格转换；时长用 `std::chrono`，字节用 `std::byte`。
- **控制流与容器**：range-for、结构化绑定、`<algorithm>` 与 C++20 ranges 表达意图；C++20 用 `contains`、`std::erase_if`。默认 `std::vector`，大小已知时 `reserve`。
- **编译期与模板**：C++17 用 `if constexpr` 取代标签分派，C++20 用 concepts 约束模板；不为普通函数引入模板或元编程。
- **并发**：RAII 锁（`lock_guard`/`scoped_lock`/`unique_lock`），条件变量带谓词等待；C++20 可取消线程用 `std::jthread` 与 `std::stop_token`。不用 `volatile` 或 `sleep` 做同步。
- **不写**：头文件中的 `using namespace`、`std::endl`、`NULL`、`typedef`、`return std::move(local)`、对 `const` 对象 `std::move`、`std::bind`、`catch (...)` 吞错。

设计新类型、模块边界或状态机时，按 [设计范式](references/design-paradigms.md) 选择：值语义、构造即有效（返回 `Result` 的静态工厂）、RAII owner、选项结构与指定初始化、封闭集合用 `variant`、依赖注入而非单例、不可变快照、Pimpl。每个范式都有适用前提，不满足时用更直接的写法。

## 项目结构与构建

- 新文件放在正确的模块层级，文件名与主要类型一致；公开头文件只放调用方需要的声明，私有类型放实现文件的匿名命名空间或私有头文件。头文件自包含，实现文件第一个 include 自己的头文件。布局与 include 规则见 [项目结构与文件摆放](references/project-layout.md)。
- 新文件和新依赖加入构建目标，并如实区分公开与私有依赖：公开头文件里用到的是公开依赖。不靠全局 include 路径或间接依赖碰巧通过编译。
- CMake 项目按目标组织（`target_*` 加 `PUBLIC`/`PRIVATE`，依赖链接导入目标），见 [CMake 参考](references/build-cmake.md)。Blade 项目在 `hdrs`/`srcs`/`deps` 中声明头文件与依赖，并设置 `visibility`，见 [Blade 参考](references/build-blade.md)。
- 第三方依赖沿用项目已有来源（包管理器、FetchContent、Blade `thirdparty/` 或 `vcpkg#`），固定版本；同一进程只保留一个版本。

## 简化实现

- 新增通用组件前，用符号、职责和调用示例搜索仓库，再检查已引入依赖的实际版本、接口、实现与测试。按“仓库已有实现 → 已引入依赖和当前标准库 → 合适的新依赖 → 参考相似实现 → 自行实现缺失部分”查找，比较语义、所有权、线程/进程模型及维护成本。
- 只为实际缺口新增代码；已有能力足够时直接调用，不再包一层纯转发 API。需要适配时只实现语义转换、资源持有或隔离职责，不复制整个框架。
- 函数围绕清楚的逻辑职责组织。优先直观控制流，在适合时提前返回以减少嵌套；不以复杂表达式、宏或压缩行数替代可读性。
- 新函数或类型应承担业务语义、不变量、资源所有权、真实复用或隔离职责。增加抽象时说明它建立的职责，以及直接实现为什么不足；concepts、coroutines、CRTP、Builder、插件接口只为当前需求服务。
- 合并重复状态前确认它们表达同一事实，不能混淆不同阶段、版本或已确认状态。清理本次改动造成的无用变量、函数和分支，不顺带清理无关代码。
- 一次使用的 RAII guard 可以有必要职责；多次使用的纯转发层也可能冗余。不要按调用次数判断抽象价值。
- 包装层若承载边界检查、错误语义、平台策略或其他可定位的约束，就有实际职责；先查相关构建条件，不因接口相似而删除安全层。删除检查的保证要求见下文“错误与边界”。

## 代码规范

- 让新增或修改的代码与相邻实现保持一致；排版、大小写和成员后缀遵循项目配置，格式化限于受影响或项目要求的范围。保留既有修改，不把偏好变成全仓迁移。
- 不改动任务之外的已有行，包括转换文件编码、改写字符转义或统一换行；确有必要时单独说明。
- 新增接口时对照同类接口的整组写法：重载集合（例如 `const char*` 与 `std::string` 两种形式、const 与非 const 版本）、命名、文档注释和测试位置与已有接口一致。
- 头文件应自包含，不依赖偶然的 include 顺序；避免不必要的依赖、暴露内部实现和头文件中的全局 `using namespace`。
- 注释解释不变量、协议约束、所有权与非直观原因，不复述代码；沿用项目的错误处理与日志习惯。

## 语义命名

- 名称的含义需要结合接口与调用方审查，格式化或命名检查通过不代表语义准确。同一概念使用同一名称，不同生命周期事实不要共用含混名称。
- 名称应区分动作与查询、字节与元素、大小与容量、注册者与活跃借用者。返回量化模式的函数不应叫 `Quantize()`；按项目风格使用 `GetQuantizationMode()` 等查询名称。
- `Close`、`Stop`、`Submit`、`Flush` 等接口应说明实际完成点。名称或合同区分发起、尝试与等待完成，不让调用者从函数体猜。
- 嵌套类型可用 `Row`、`ReadBatch` 等局部名称。避免堆叠已由作用域提供的上下文，也不为缩短名称引入 `mgr`、`impl2` 等含混缩写。
- 有含义不同的布尔选项时，优先具名枚举或已有 options 类型；不要为机械消除一个 bool 参数新建框架。

## 类型与所有权

- 优先局部值对象；需要动态独占所有权时用项目认可的独占 owner。只有确实共同决定销毁时才用 `shared_ptr`。
- 引用、指针、`span`、`string_view` 都不延长底层对象寿命。接口应能看出谁持有资源、谁借用、借用到何时结束；异步保存借用前必须证明 owner 的存活期。
- 文件、映射、锁、登记句柄和额度用 RAII 绑定实际释放职责。确需自定义资源 owner 时明确 moved-from 状态。
- `const` 约束当前访问路径，不代表对象没有可变别名，也不自动保证线程安全。不要为了全员 `const` 破坏必要的移动或赋值语义。
- 用现有类型、`enum class`、具名结果或受约束构造表达业务不变量。只有单位混淆、非法组合或状态转移确有风险时才增加包装类型。
- `class` 用于维护需要共同成立的不变量，`struct` 适合字段独立的数据描述。不要只因存在成员函数就更换关键字，也不为每个整数引入强类型。
- 不以默认构造的“半有效对象”隐藏失败；若协议必须两阶段初始化，显式表示并限制状态。
- 模板、无异常环境、C ABI、自定义 allocator 等场景服从项目约束，不机械禁止原始句柄或底层操作。将必要的危险操作收敛到可审计的边界。

## 错误与边界

- 遵循项目的 `Status` / `Result` / 异常策略，不并行引入第二套错误框架。
- 区分输入错误、可恢复失败和程序内部不变量。断言按项目机制表达程序错误，不能代替用户输入校验或正常错误传播；移除运行时检查前确认 Release 配置仍满足合同。
- `optional` 表示合法缺席；不得把解析失败、超时或短读变成“没有值”而丢掉失败原因。保留项目区分的 not-found 与 error 语义。
- 校验放在真实输入、信任与状态变化边界。删除校验时指出建立保证的类型/代码位置，并检查异步、并发、RPC、共享内存后保证是否仍然有效。
- 保留可操作的错误上下文；避免每层重复记录同一错误。只在恢复、语义转换或明确终止边界捕获异常。析构不抛出；需要反馈关闭失败时提供项目风格的显式关闭操作。
- 对长度、偏移和容量检查溢出、符号转换与边界。精度或数量不一致时修复合同，不能截短结果、放宽阈值或吞错来让测试通过。

## 验证与交付

交付前逐条复查本次改动：

1. 写法：用到的特性和头文件不超出项目标准与库范围；在此范围内，没有 owner 之外的裸 `new`/`delete`、C 风格转换、项目约定之外的输出参数、两阶段初始化、只有一个实现的接口、到处 `shared_ptr`、复述代码的注释，C++11 起不用 `NULL`。
2. 结构：实现没有无职责的层次或重复状态；文件位置、头文件公开范围和构建依赖正确。
3. 命名：名称准确表达行为、单位与完成点。

运行改动所需的编译、行为测试及项目要求的检查。项目配置了警告选项、`-Werror` 或 clang-tidy 时，对改动文件运行，新代码不引入新的诊断。新增测试应覆盖真实回归或合同，避免只断言实现细节。简单可逆修改不强制新建测试。

报告：改变了什么行为、关键职责为何这样划分、实际运行了哪些验证、还有哪些限制。没有执行的检查明确标为未执行；代码推断不写成实测收益。
